## 1. 화면 (2026-09-13 실측 · **타일은 2026-09-14 회차 17 에 16px 으로 다시 쟀다**)

**조건: `stretch/mode=viewport` + `scale_mode=integer` + `aspect=keep`, 창 override 1920×1080**

실제로 창을 띄워서 잰 값이다 (`scripts/main.gd` 가 찍는다):

```
VIEWPORT 960 x 540
WINDOW   1920 x 1080
SCALE    2.00 x
```

| 값 | 무엇 | 왜 그 값인가 |
|---|---|---|
| **960 × 540** | 논리 해상도 (= 보이는 월드 범위) | **1080p 정수 2배 · 4K 정수 4배.** 소수 배율은 도트 하나를 화면에서 어떤 건 1px, 어떤 건 2px 로 만들어 걸을 때 얼룩이 흐른다 |
| **1920 × 1080** | 창 크기 | 논리 화면을 정확히 2배로 늘려 붙인다 |
| **2.00 ×** | 실측 배율 | 정수다 |
| **60 × 33.75 칸** | 보이는 타일 수 | 타일 **16px** 기준(48 → 32 → 16, 사람이 30·40·60 칸을 구워 보고 60 을 골랐다). 16px 은 스타듀·코어키퍼가 **아트를 그리는 해상도**다 — 걔들은 4배로 키워 30칸을 보여주고 우리는 2배로 키워 60칸을 본다. `test_visible_tiles` 가 강제한다 — **해상도와 타일 둘 중 아무거나** 바뀌면 빨강 |

**대가**: UI 도 960×540 좌표계에서 만들어야 하고, 폰트가 통째로 2배로 늘어나므로
**비트맵 픽셀 폰트가 필요하다** — 기본 폰트는 늘리면 뭉갠다.

### 실측 게이트 `tools/tests/measure_window.gd` 의 VIEW 절반 (2026-09-14 실측)

> **회차 14 에 `measure_view.gd` 와 `measure_draw.gd` 를 한 파일로 합쳤다** — 둘 다
> 창이 필요하고 둘 다 메인 씬을 세운다. 창 여는 횟수가 곧 포커스 도둑질이다 (11절).
> **잰 값은 글자 하나 안 달라졌다** (아래 블록은 합친 뒤 다시 잰 것이다).

위 표는 `test_project_settings.gd` 가 **project.godot 의 글자**를 읽어 강제한다.
글자가 맞아도 실행 중에 카메라 줌이나 창 크기를 만지면 눈에 보이는 칸은 달라진다 —
그래서 **실제 창을 띄워** 다시 잰다 (`check.sh tests` 가 `--headless` 없이 부른다).

```
VIEW 논리 960x540 · 창 1920x1080 · 배율 2.00x · 카메라 1.00x · 타일 16px · 보이는 칸 60.00 x 33.75
VIEW ok (드라이버 macOS · 프레임 5)
```

- 배율은 나눗셈이 아니라 **`root.get_final_transform()`** 에서 잰다.
- 보이는 칸은 **`get_canvas_transform()`** 으로 월드 좌표로 환산해서 잰다 —
  카메라 줌이 곧 시야 이득이라 여기를 막아야 한다 (BACKLOG P1 「줌 없음」).

**대조군 2종** (`redteam.sh` 에 박아 뒀다):

| 일부러 깨뜨린 것 | 단위 검사 | 화면 실측 |
|---|---|---|
| 카메라 `zoom` 을 (2,2) 로 | (2026-09-13: `18 passed`) | **잰 값 보이는 칸 15.00 x 8.44** ✅ (타일 48 일 때는 10.00 x 5.62 · **타일 16 이면 30.00 x 16.88**) |
| 실행 중 `window_set_size(1600, 900)` | `18 passed, 0 failed` | **잰 값 창 1600x900 · 배율 1.00x** ✅ |

두 번째가 정수 배율의 성질을 그대로 보여준다: 1600/960 = 1.66 이 아니라 **1** 로 떨어진다.

**첫 줄은 회차 8 에서 겨눌 곳이 바뀌었다.** 그때는 `main.tscn` 에 카메라를 하나 덧붙였는데,
진짜 카메라가 생긴 뒤로는 **먼저 트리에 들어온 플레이어의 카메라가 화면을 잡는다(선착순)** —
덧붙인 카메라는 아무 일도 안 한다. **가짜 대조군이 될 뻔한 자리다.** 지금은 `player.tscn` 의
그 카메라의 줌을 직접 건다. 대신 단위 검사(`test_camera_zoom_is_one`)도 같이 잡으므로,
「단위는 초록인데 실측만 잡는」 쪽은 8절의 **실행 중 줌**이 맡는다.

### 1b. 창을 게임 크기에 맞춘다 — **띠 0** (2026-09-15 · 회차 33 실측)

**조건: 16" MacBook Pro (M5 Pro · macOS 25.6) · 화면 3456×2234 px · `screen_get_scale` 2.00 ·
dpi 255 · 논리 960×540 · `stretch/mode=viewport` + `aspect=keep` + `scale_mode=integer`**

사람이 「화면이 안 맞는다」고 **두 번** 지적한 자리다. 창 override 1920×1080 은 이 화면의
**가로 55.6%** 밖에 안 덮었고, 그 다음에 켠 **전체 화면은 576×548 px 을 띠로 버렸다.**

**`main.gd` 가 이제 `Display.fit_window()` 로 창을 `논리 × N` 에 맞춘다.**

```
DISPLAY 쓸 수 있는 화면 3456x2168 · 논리 960x540 · 배율 3x · 창 2880x1620
        · 띠 0x0 · 화면 남음 576x548 · 묶는 축 가로
VIEW 논리 960x540 · 창 2880x1620 · 배율 3.00x · 그린 크기 2880x1620 · 띠 0x0
     · 화면 3456x2168 · 카메라 1.00x · 타일 16px · 보이는 칸 60.00 x 33.75
POS 창 자리 (288, 340) · 크기 (2880, 1620) · 모드 0(창)
```

**자리는 계산과 맞는다**: x = (3456−2880)/2 = **288** · y = 66 + (2168−1620)/2 = **340**.
쓸 수 있는 곳이 (0,**66**) 에서 시작하므로 그 66 을 안 더하면 창이 33px 위로 밀린다.

**셋 중 둘만 고를 수 있다고 적었던 것이 틀렸다.** ⓐ 띠 없음 · ⓑ 정수 배율 ·
ⓒ 누구나 같은 범위 — **셋이 다 된다.** 앞 회차는 「화면 크기가 고정」이라고 두고 풀어서
ⓐ 를 버렸는데, **고정인 것은 전체 화면일 때뿐이었다.** 창 크기는 우리가 정한다.

**그림의 크기는 한 픽셀도 안 달라졌다** — 전체 화면도 창도 같은 3배 · 2880×1620 이고
보이는 칸도 60.00 × 33.75 그대로다. 전체 화면이 더 준 것은 **검은 테두리뿐**이었다.

#### 전체 화면을 그만둔 근거 — 창 모드별 실측 (`window_set_mode` 뒤 12프레임)

| 모드 | 창 크기 | 자리 | 배율 | 그린 크기 | 띠 |
|---|---|---|---|---|---|
| 0 창 (override) | 1920×1080 | (768, 610) | 2.00x | 1920×1080 | 0×0 |
| 2 최대화 | 3456×2104 | (0, 130) | 3.00x | 2880×1620 | 576×484 |
| 3 전체 화면 | 3456×2168 | (0, 66) | 3.00x | 2880×1620 | **576×548** |
| 4 독점 전체 화면 | 3456×2168 | (0, 66) | 3.00x | 2880×1620 | 576×548 |
| **0 창 (`fit_window`)** | **2880×1620** | **(288, 340)** | **3.00x** | 2880×1620 | **0×0** |

전체 화면에서 **가로 576 은 못 줄였다** — 3456 ÷ 960 = **3.6** 이라 정수 배율은 3 이 끝이고,
4 로 올리면 3840 px 이 되어 화면 밖으로 384 px 이 잘린다. 잘린 만큼은 「남이 보는 것을
내가 못 보는 것」이라 ⓒ 가 깨진다. 세로 548 은 화면 비율 **1.594 대 16:9 의 1.778** 차이
그 자체다(`aspect=keep` 은 배율이 하나라 **가로가 묶는다**). **전체 화면에 남아 있는 한
띠 0 은 못 나온다** — 960 의 배수가 3456 에 없기 때문이다. 그래서 전체 화면을 그만뒀다.

**전체 화면 창 = `screen_get_usable_rect().size` 였다** (3456×2168 · 자리도 (0,66) 으로 같다).
`screen_get_size()` 로 재면 **세로를 66px 더 크게** 본다 — 메뉴 막대·노치 띠는 창에 안 온다.

#### 게이트가 무는 자리 — **등식 둘이 필요하다**

「띠 = 0」 하나로는 **아무것도 안 잡는다**:

- override **1920×1080 은 정확히 2배**라 `fit_window` 를 통째로 안 불러도 **띠가 0 이다.**
  회차 33 전까지 이 건이 게이트에 안 걸린 이유가 정확히 이것이다.
- 한 단계 작은 창(1920×1080)도 띠가 0 이다 — 화면의 3할만 쓰는 창인데 초록이다.

그래서 VIEW 는 **띠 = 0** 과 **배율 = `max_scale(쓸 수 있는 화면, 논리)`** 를 **둘 다** 묻는다.
띠는 **창에서** 뺀다 — 화면에서 빼면 창 모드에서 「바탕 화면이 보인다」를 띠로 세게 된다.

**`content_scale_factor` 는 여기서 아무 일도 안 한다** (실측): `2.0/3.0` 을 걸어도
배율이 3.00x 그대로였다. `stretch mode=viewport` + `scale_mode=integer` 조합에서는
창 크기만이 배율을 정한다 — 그래서 대조군은 **창 크기**를 겨눈다.

#### 대조군 — 다섯이 **서로 다른 등식**에서 잡힌다 (2026-09-15 · 회차 34 실측)

| 일부러 깨뜨린 것 | 단위 175개 | 띠 | 배율 | 자리 | 잡은 줄 |
|---|---|---|---|---|---|
| ① `main.gd` 의 `fit_window()` 호출을 지움 | **전부 초록** | **0×0** | 2.00x | — | **배율** (기대 3) |
| ② `fit_window` 이 전체 화면으로 돌아감 | 전부 초록 | **576×548** | 3.00x | — | **띠** |
| ③ 창을 한 단계 작게 (`N−1`) 잡음 | 전부 초록 | **0×0** | 2.00x | — | **배율** (기대 3) |
| ④ `max_scale` 의 내림을 반올림으로 | 빨강 | 0×0 | 4.00x | — | 단위 + **창이 화면 밖** |
| ⑤ `avail_rect` 을 `screen_get_size()` 로 | 전부 초록 | **0×0** | 3.00x | **340 → 307** | **자리** |

**① 과 ③ 이 이 절의 존재 이유다**: 배선을 통째로 빼도 **띠가 0 이다** — override 1920×1080 이
이 화면에서 정확히 2배라서다. 「띠 = 0」만 묻는 게이트는 다섯 중 **넷을 놓친다**(②만 잡는다).
**⑤ 는 크기가 한 픽셀도 안 변한다** — 자리를 안 재면 다섯 중 셋이 빠져나간다.

`REDTEAM 10 잡음, 2 놓침 · 103개 건너뜀 (--only 회차 33)` — **다섯은 다 잡았다.**
놓친 둘은 앞뒤의 「손 안 댄 상태는 초록이다」·「원복하면 다시 초록이다」이고, 창이 아니라
**REGROW 게임 시계가 흔들린 것**이다 (`0.30초 도는 동안 0.39초` · 허용 0.05초).
같은 트리에서 `run-contract.sh` 를 **혼자 돌리면 `ALL GREEN`** 이다 — 상태 검사를 연달아
12번 부르는 부하에서만 난다. 전체 판(`.loop/runs/001/redteam-full.txt` · `REDTEAM 110 잡음,
5 놓침`)에서도 **이 묶음 다섯은 전부 초록이었다** — 놓친 다섯은 전부 다른 묶음이다.

#### 사람이 직접 띄운 창 — **게이트 밖에서 한 번 더** (2026-09-15 실측)

게이트는 `--script` 로 메인 씬을 세운다. 사람은 `godot --path .` 로 띄운다 — **그 둘이
같은 창인지는 아무도 안 쟀다**. 이 건이 두 번 지적당한 자리라 손으로 한 번 맞대 봤다:

```

**VIEW 가 재는 값과 한 자리도 안 다르다.** 창·배율·띠·보이는 칸 넷이 다 같다.

## 2. 격리 — **macOS 는 XDG 를 무시한다** (2026-09-13 실측)

**이걸 안 재고 넘어갈 뻔했다.** `XDG_DATA_HOME` 등을 설정해두고 「격리했다」고 믿는 것이
정확히 가짜 게이트다.

| 방법 | `user://` 가 실제로 간 곳 | 홈의 Godot 디렉터리 |
|---|---|---|
| `XDG_*` 만 설정 | `~/Library/Application Support/Godot/app_userdata/Naru` | **mtime 이 실행 시각으로 갱신됨** ❌ |
| **`HOME` 을 돌린다** | `.godot-home/Library/Application Support/Godot/app_userdata/Naru` | **mtime 안 바뀜** ✅ |

- 그래서 `tools/loop/godot.sh` 는 **`HOME` 자체를 프로젝트 안으로 돌린다.**
  `XDG_*` 도 같이 두는 것은 리눅스에서 도는 경우를 위해서다.
- **격리는 설정이 아니라 「입구」로 지켜진다.** `test_isolation.gd` 가
  `OS.get_user_data_dir()` 이 프로젝트 안인지 재므로, **`godot.sh` 를 우회한 실행은
  그 자리에서 빨개진다.** 실측:

  ```
  FAIL test_isolation.gd :: test_user_data_is_project_local
       — 잰 값: /Users/tuna/Library/Application Support/Godot/app_userdata/Naru
  ```

### 대조군 — 게이트가 진짜로 잡는지 잰 값

### 대조군이 **헛도는 길** — 치환이 빗나간다 (2026-09-15 · 회차 35)

전체 쓸기 `REDTEAM 110 잡음, 5 놓침` 중 **넷은 게이트가 약한 게 아니었다.** 대조군이

**규칙**: 치환은 바뀌는 조각만 집는다. 인자 목록·배열 내용·오른쪽 식은 `.*` 로 둔다 —

#### 높이 문턱은 **검사 쪽에 다시 적는다** (2026-09-15 · 회차 35 에 고쳤다)

`test_ore_only_on_high_ground` 이 `WorldObjects.ORE_MIN_HEIGHT` 를 읽어서 견주고 있었다 —
**재는 값과 기대값이 같이 움직였다.** 상수를 0.0 으로 내리면 기대도 0.0 이 되고,
해수면이 0.30 이라 `h <= 0.0` 인 땅이 아예 없어서 **초록**이다. 대조군 ⑤(「광물 높이
문턱을 없앤다」)가 회차 24 부터 그래서 아무것도 안 잡았다.

검사 쪽에 `ORE_FLOOR := 0.55` 를 다시 적고, **상수와 배치를 따로** 묻는다. 둘 중 하나만
있으면 빠져나가는 길이 남는다 — 상수를 그대로 두고 `at_height` 의 `if h > ORE_MIN_HEIGHT`
만 걷어내면 값은 멀쩡하고 배치만 해안까지 내려온다. **한쪽으로만 막는 문턱이다**:

| **6.0 x 4.0 px** | 상자 반크기(`HALF`). **네모가 아니라 발밑 직사각형이다** (회차 16) — 12 × 8. **숫자가 아니라 식이다**: `Vector2(TILE * 0.5 - 2.0, TILE * 0.25)` — 회차 17 에 타일만 반으로 내렸더니 따라왔다 |
| **12 px** | 상자 폭. 16 타일 안에서 **양옆 2px 씩 남는다** — 박아 두면 타일이 작아질 때 안 따라와 1칸 통로에 낀다 |
| **8 px** | 상자 높이 = **발밑 반 칸**. 몸통은 32px(2칸)인데 상자는 그 아래끝 반 칸뿐이라 **머리가 위 칸에 걸쳐도 안 막힌다** (코어 키퍼 관례) |
| **1.99 px** | 벽에 붙었을 때 **그리는 네모가 막힌 칸에 걸치는 몫**. 몸 반폭 8 - 상자 반폭 6 - 틈 0.01. **타일이 반이 돼도 안 바뀐다** — `HALF` 의 2px 여유가 절대값이라서다. 몸통이 1.5칸이던 회차 15 까지는 **10 px** 였다 |
| **0.01 px** | 벽에 붙일 때 남기는 틈(`EPS`). 0 이면 붙은 칸이 겹친 칸으로 읽혀 다음 프레임이 흔들린다 |

| **3.094 µs** | 「이 칸이 막나」 한 번 (10만 회 309.4 ms · 막힘 67.7%). 한 틱에 네 번쯤 묻는다. 회차 15 에 3.345 · 16 에 3.186 — **같은 코드의 판 사이 흔들림**이다. 막힘 67.7% 는 세 회차 내내 같다(칸은 안 바뀌었다) |

**몸이 타일보다 좁아야 하는 이유**: `HALF.x` 가 타일 반(8)과 같으면 폭 1칸(16px) 통로에서
부동소수 한 톨에 걸려 낀다. `6 < 8` 은 검사(`test_body_is_narrower_than_a_tile`)가 지킨다.

### 값이 셋으로 갈라져 있었다 — 회차 16 에 한 군데로 모았다

회차 15 까지 사람의 몸은 **세 개**였다: 그리는 네모 48×48 · 충돌 상자 28×28 ·
`player.tscn` 의 `RectangleShape2D` 48×48 (아무도 안 읽는 값). 셋이 따로 놀아서
벽에 붙으면 네모가 막힌 칸에 **10px 걸쳐** 보였다 — 좌표는 맞는데 그림이 틀렸다.

지금은 **타일 하나에서 다 따라 나오고**, 검사가 셋을 한자리에 묶는다:

| | 값 | 어디서 나오나 |
|---|---|---|
| 그리는 네모 | **16 × 32** (1칸 폭 × **2칸 키** — 회차 17) | `player.tscn`. `test_player_scene.gd` 가 `TILE` 에 묶는다 |
| 충돌 상자 | **12 × 8** (발밑 반 칸) | `WorldCollide.HALF` — `TILE` 에서 나오는 식이다 |
| 씬의 상자 모양 | **12 × 8** | `player.tscn`. 같은 검사가 `HALF * 2` 와 맞춘다 |

**원점이 발밑으로 내려갔다.** `position` 은 이제 충돌 상자의 한가운데 = **서 있는 칸**이고,
몸통은 그 위로 선다(y −28 .. +4). 코 네모도 원점이 아니라 **몸통 한가운데**를 돈다 —
축마다 반지름이 달라서(옆 8 · 위아래 16) 「방향 × 거리 하나」로는 안 된다.
카메라는 **원점(발밑)을 그대로 비춘다** — 몸통 한가운데보다 12px 아래다.
960×540 에서 2%라 바꾸지 않았다. 올릴지는 사람이 볼 일이다.

### 미끄러짐은 **축을 따로 푸는 것**에서 나온다

x 를 풀고 y 를 푼다 — 막힌 축만 죽고 나머지는 그대로 간다.
「벽에 닿았으니 통째로 정지」가 아니고, 남은 몫을 다시 정규화하지도 않는다.
**물리 엔진을 안 쓴다**: 65536칸에 정적 몸을 세울 수 없고, 창 주변만 세우면 결과가
「지금 무엇이 세워져 있나」에 달린다. 격자에 대고 풀면 **같은 입력이 언제나 같은 자리**다
(GDD D-1 서버 재현성 · C-4 원정 보고 검증).

### 실측 게이트 `tools/tests/measure_collide.gd` (2026-09-14 실측)

`check.sh tests` 가 `WORLD` 뒤에 부른다. **메인 씬을 통째로 띄운다** — 플레이어 씬만
띄우면 `main.gd` 의 배선이 안 잡힌다. 씨앗에서 **곧은 남북 해안**(땅 4칸 × 7줄 + 옆은 바다)을
스폰에서 가까운 순으로 찾아, 활주로 3칸에서 걸어 부딪힌다.

```

**「걸침」이 회차 16 에 늘어난 넷째 판정이다.** ①②③ 이 전부 맞아도 **그리는 네모**가
상자보다 한참 넓으면 사람 눈에는 몸이 바다에 잠긴 채 서 있는 것으로 보인다 —
상수가 아니라 **살아 있는 씬의 `Body` 를 읽어서** 잰다. 상한 2.5px.

**미끄럼 구간은 이제 초가 아니다** (회차 17). 1.2 → 0.9 (회차 15) 는 손으로 줄인 값인데,
타일이 또 반이 되자 0.9 는 다시 틀렸다: 169.71 × 0.9 = 152.7px 라 곧은 해안 7줄이
224 → **112px** 로 줄어든 뒤로는 미끄럼이 해안 밖에서 끝난다.
**그 상수는 처음부터 「해안 몇 줄」이었다** — 그래서 `_slide_sec()` 가 기하에서 푼다:

```
내려갈 수 있는 거리 = (RUN - 0.5) × TILE - HALF.y = 6.5 × 16 - 4 = 100 px
미끄럼 시간 = 100 × SLIDE_FILL(0.8) ÷ 169.71 = 0.471 s   → 세로 82.02 px · 가로 49.99 px
```

남은 0.2 는 물리 틱 경계(대각 한 틱 2.83px)의 여유다. 가로 49.99px 는 활주로
(`TILE × (RUNWAY + 0.5) - HALF.x` = 49.99px)를 정확히 채워 벽에 붙는다.
**세로 속력은 173.25 px/s 로 잡혔다** — 169.71 ±5 안이다(틱 경계로 한 틱이 남는다).

**해안 칸은 안 바뀌었다 — 바뀐 것은 한 칸의 px 다.** 바다 면 11040 → 7360 → **3680** 은
물리가 아니라 자(尺)다: 해안 칸 230 이 그대로 230 × **16** = 3680 px 다 (32 이던 때 7360 ·
48 이던 때 11040). 멈춘 자리 **3673.99 = 3680 - 6 - 0.01** 이다. 세 가지를 같이 본다:
① 바다 면 앞에 서는가 ② **몸이 바다에 걸치지 않는가**(좌표만 맞고 반 칸 잠기는 경우가 있다)
③ 옆으로 가려던 몫이 살아 있는가(169.71 ±5).

### 비추는 점은 발이 아니라 **몸통 한가운데**다 (2026-09-15 · 회차 36 실측)

회차 16 이 원점을 발밑으로 내리면서 **화면 중심이 발이 됐다** — 화면의 아래 절반이
플레이어 뒤쪽 땅이라 가는 쪽이 그만큼 덜 보인다. 사람이 몸통 한가운데로 정했다.

**12px 다 — 백로그에 적힌 「16px 위」가 아니다.** 몸통 네모는 발밑 상자의 아래끝
(`WorldCollide.HALF.y` = 원점보다 4px 아래)에서 시작해 32px 올라간다:

```
몸통 한가운데 = body.position.y + body.size.y / 2 = (4 − 32) + 16 = −12
              = WorldCollide.HALF.y − PlayerMotion.TILE
```

16 은 **몸통 키의 절반**이고, 그 둘이 갈라지는 만큼이 발밑 상자의 반높이 4px 다.
**`player.gd` 의 코·도구가 이미 같은 점을 쓴다** (`_body.position + _body.size * 0.5`) —
16 으로 두면 「몸통 한가운데」라는 이름의 점이 **둘**이 된다.

`scenes/player.tscn` 의 `Camera` 에 `position = Vector2(0, -12)` 하나로 끝난다.
코드는 한 줄도 안 늘었다 — 아래 「코드가 아니라 부모-자식」이 그대로 산다.

### 카메라는 **코드가 아니라 부모-자식**이다

`Camera2D` 를 플레이어 씬 안에 둔다. 매 프레임 `camera.position = player.position` 을
쓰지 않는다 — 그건 물리(60Hz)와 그리기 사이에 **한 틱 뒤처질 자리**를 만들고,
프레임률에 따라 뒤처지는 양이 달라진다. 실측 편차가 **0.0000 px** 인 것이 그 값이다.

같은 이유로 `position_smoothing` 을 끈다. 부드럽게 따라오는 화면은 예쁘지만
**「같은 입력 = 같은 화면」이 아니다.** 켜 보면 최대 편차가 **82.10 px** 로 벌어진다(아래 표).

### 줌은 **1 이다** — 해상도가 시야 이득이 되면 안 된다

창이 큰 사람이 더 멀리 보면 그건 설정이 아니라 **유리함**이다 (BACKLOG P1 「줌 없음」).
그래서 두 군데서 막는다: 씬에 박힌 글자(`test_camera_zoom_is_one`)와
**실행 중의 캔버스 변환**(`measure_camera.gd` · `measure_window.gd` 의 VIEW).

### 사라진 값 — `tile_offset`

회차 7 의 `tile_offset = (118, 123)` 이 없어졌다. **화면 칸 = 월드 칸**이다 (7절).
`WorldCollide.solid_from_seed` 의 이동량 인자와 `main.gd` 의 `screen_of()` 도 같이 지웠다.

### 색이 곧 지형이다 — 덧칠이 아니다

물이냐 땅이냐는 **`WorldGen.tile_at` 이 정한다.** `WorldView` 가 `h > SEA_LEVEL` 을
다시 쓰지 않는 이유가 이것이다 — 두 벌을 두면 언젠가 한쪽만 고쳐져 **보이는 땅에
못 서는 날**이 온다. 그 안에서의 명암만 높이로 섞는다.

**흔들기는 세 채널에 같은 양을 더한다**(`TINT` ±0.035 = 8비트로 ±9). 그래서
**물은 언제나 b > g > r · 땅은 언제나 g > r > b** 이고, 이 부등식을 `test_world_view.gd`
가 7396칸으로 잰다. 곱하거나 채널마다 다르게 흔들면 **물처럼 보이는 땅**이 생긴다.

`DEEP_AT = -0.25` 는 고른 값이 아니라 **계산된 값**이다: 월드 밖은 감쇠가 1.25 로
포화하므로 높이가 `0.35 + 0.65 - 1.25 = -0.25` 를 넘을 수 없다 → **월드 밖은 자동으로
정확히 `DEEP`** 이고 분기가 필요 없다 (6절의 「섬 모양은 부등식이 보장한다」와 같은 수법).

### 화면이 단색이면 안 된다 — 칸마다 흔드는 진짜 이유

| | 칸 | 색 수 | 가장 넓은 한 색 |
|---|---|---|---|
| 임시 격자 (회차 8) | — | 3개 | **50.0%** |
| 진짜 월드 · 타일 48 (회차 9) | 273 | **217개** | **1.3%** |
| 진짜 월드 · 타일 32 (회차 15) | 558 | **349개** | **1.3%** |
| 진짜 월드 · 타일 16 (회차 17) | 2135 | **867개** | **0.8%** |

**검사의 문턱도 같이 올렸다**: 색 수 100 → 200 → **743개**. 273칸에 100개는 37% 였는데
칸만 늘리고 문턱을 두면 게이트가 그 비율만큼 **헐거워진다** (`test_a_screenful_is_not_flat`).
**세는 창도 화면을 따라 넓혔다** (회차 17: 31×18 → 61×34칸). 그 창의 실측은 **798개 /
2074칸**(38.5%)이다 — 558칸 349개(62.5%)보다 비율이 낮다. **색이 포화한다**: 한 화면이
넓어져도 높이 구간이 그대로라 새 색이 그만큼 안 늘어난다.

흔들기가 없으면 스폰 주변은 전부 풀밭이라 한 화면이 거의 단색이 되고,
`shot.sh --max-flat` 이 **아무것도 안 잡는 공허한 상한**이 된다.
16px 격자가 눈에 남는 것은 덤이 아니라 필요다 — 240 px/s 가 15칸/초로 보이는지
**사람이 걸어서** 확인하는 유일한 방법이다.

### 색 캐시 — 프레임마다 다시 계산하지 않는다

**회차 24 에 13.0 → 7.9 ms 로 내려갔다** (프레임 예산의 78% → **47%**). 나무·돌·광물이
얹혔는데도 내려간 이유는 하나다: 지형색이 `height_at` 과 `tile_at` 을 따로 불러
**잡음을 두 번 돌고 있었다.** `WorldGen.kind_at_height` 로 높이 한 번에서 지형까지 나온다 —
한 칸 **6.71 → 3.32 µs** (2026-09-15 실측 · 1만 칸 평균 · 헤드리스).
아래 문단의 13.0 ms 는 회차 17 의 값이고, 결론은 그대로다 — 스크롤은 여전히 해야 한다.

13.0 ms 는 나무도 몹도 UI 도 없던 회차 17 의 **78%** 다. 그래서 **칸이 아니라 보이는 범위가
바뀔 때만** 다시 채운다(`main.gd` 의 `_cache` / `_cache_range`).
**48 px(3칸) 걷는 동안 5번** 찼다 — 240 px/s 면 한 축당 초당 15번이라 평균 4배 싸다.
**타일이 반이 될 때마다 한 판은 4배 비싸지고 빈도는 2배가 된다** — 곱하면 8배다.
회차 15(48 → 32)까지는 22%라 여유가 있었지만 **16px 에서는 한 번 채울 때마다
프레임을 놓친다.** 고치는 길은 「덜 자주」가 아니라 **범위가 한 줄 밀릴 때 그 줄만
채우기**(스크롤)다 — BACKLOG 에 넘겼다.

**대가는 상해도 눈에 안 보이는 것이다** — 캐시가 안 버려지면 화면이 월드에서 미끄러진다.

## 10. 방향 게이트 — 합성 입력 (2026-09-14 실측)

**조건: 씨앗 20260914 · 논리 960×540 · 줌 1 · 60Hz · Godot 4.7 · macOS**

9절 끝의 흔들림을 고쳤다. `measure_facing.gd` 는 이제 **진짜 커서를 안 뺏는다** —
메인 씬을 제 `SubViewport` 에 세우고 합성 `InputEventMouseMotion` 을 밀어 넣는다.

### 왜 루트 뷰포트로는 안 되나

**루트 뷰포트의 `get_mouse_position()` 은 매번 OS 커서를 되묻는다.** 그래서
`warp_mouse` 로 옮겨 놔도 사람이(또는 다른 프로세스가) 커서를 건드리면 그 값이 이긴다.
**SubViewport 는 밀어 넣은 이벤트만 본다:**

| | 이벤트를 (700,111) 로 밀어 넣은 뒤 | `warp_mouse(5,5)` 한 뒤 |
|---|---|---|
| `SubViewport.get_mouse_position()` | (700, 111) | **(700, 111) — 안 움직인다** |
| `root.get_mouse_position()` | (-104, 225) | (2, 2) |

헤드리스에서도 같다 (SubViewport 쪽은 두 번 다 (700,111)).

### 대조군 — 커서를 흔들면서 돌렸다

두 번째 Godot 을 띄워 매 프레임 `warp_mouse` 로 커서를 휘젓는 **방해 프로세스**를
만들어, 옛 게이트와 새 게이트에 같은 방해를 걸었다. 이걸로 **네 회차짜리 흔들림이
처음으로 재현됐다** — 전에는 사람이 마우스를 만질 때만 우연히 나타났다.

| 게이트 | 방해 | 결과 |
|---|---|---|
| 옛 (진짜 커서) | 있음 | **FAIL 13개 · 7구간 전부** · 커서 각 `-155.5°`·`-137.3°`·`-158.2°` (기대 0°·90°·180°) |
| 새 (합성 입력) | 있음 · 헤드리스 | **7구간 전부 ok** · 커서 각 `0.0°`·`90.0°`·`180.0°`·`-90.0°`·`46.0°`·`60.0°` — **오차 0** |
| 새 (합성 입력) | 있음 · 창 띄움 · 15회 | **15/15 초록** |

### 숨어 있던 두 번째 버그 — 유휴 프레임 ≠ 물리 틱

방해를 걸고 재다가 **마우스와 무관한** 실패를 찾았다. 마우스를 안 건드리고
**부하만** 준 12회 중 1회, 첫 구간이 `커서 0.0°`(겨눔은 정확)인데
`방향 (-1,0)`(기대 (1,0))으로 빨갰다.

**원인**: `facing` 은 `_physics_process` 가 정하는데 게이트는 **유휴 프레임**을 셌다.
부하가 걸리면 유휴 4프레임이 물리 한 틱도 못 품는다 — 겨눔은 맞고 방향만 한 틱
뒤처진다. **하필 첫 구간인 이유**: 밀어 넣기 전 SubViewport 의 커서 기본값이 (0,0) 이라
플레이어(화면 한가운데) 기준 **−151°** 다. 플레이어가 먼저 `LEFT` 를 잡아 두고 있다.

**고친 것**: `Engine.get_physics_frames()` 로 **물리 틱을 센다** (`SETTLE_TICKS = 2`).

| 언제 | 부하만 · 창 띄움 | 마우스 방해 · 창 띄움 |
|---|---|---|
| 유휴 프레임을 셀 때 | **12회 중 1회 빨강** | 8회 중 1회 빨강 |
| 물리 틱을 셀 때 | **15회 중 0회** | **15회 중 0회** |

### 구멍은 그대로 막혀 있나 — FACE 대조군 4종

SubViewport 로 옮기면서 **덮던 것을 잃지 않았는지** 물었다. 넷 다 잡는다:

| 대조군 | 잰 값 |
|---|---|
| ① 노드가 커서를 안 읽는다 (`aim_at(...)` → `pass`) | **FAIL 4개** |
| ② 히스테리시스를 건너뛴다 (`resolve` → `nearest`) | **FAIL 1개** (46° 구간) |
| ③ 방향은 맞는데 코가 안 돈다 (`_place_nose()` 제거) | **FAIL 4개** |
| ④ **캔버스 변환을 빼먹는다** (`get_global_mouse_position` → `get_viewport().get_mouse_position`) | **FAIL 6개** |

④ 는 **회차 11 에 새로 넣었다.** SubViewport 로 옮겼으니 「카메라의 캔버스 변환을
정말 타는가」를 물어야 한다 — 안 그러면 커서를 창 좌표 그대로 읽어도 통과하는 게이트가
된다. 스폰이 칸 (128,128) 이라 변환의 평행이동이 **6000 px 대**다. `redteam.sh` 는
**30 → 31개**가 됐다.

### 덤 — 기계를 안 뺏는다

게이트가 **헤드리스로 돈다**(창을 띄워도 통과한다 — 둘 다 쟀다). 이제 `check.sh tests`
어디에서도 `warp_mouse` 를 안 부른다. 창을 띄우는 게이트는 `measure_view.gd` ·

상태 검사 한 판 **`ALL GREEN`(기준 6개 · 32.81s)**.

**이 게이트는 여전히 나무만 본다** (회차 37). 겨누는 것이 「main.gd 가 시계를 돌리나」라
종류를 늘려도 새로 열리는 고장이 없다 — 돌·광물의 날 수와 큐 순서는 단위 검사가

**시계 오차 0.000000초 / 0.305초**가 이 게이트의 첫 줄이다. `world.now` 를 실제로 흐른
프레임 delta 의 합과 견준다 — main.gd 가 `tick` 을 안 부르면 **구간 전체가 어긋나고**,
현실 시계를 주워 오면 값이 안 맞는다.

### 15b. 시계 오차는 **0 이다** — 허용치가 아니라 등식이었다 (2026-09-15 · 회차 35 실측)

**조건: 위와 같다 · `--script res://tools/tests/measure_headless.gd -- regrow` 로
REGROW 만 · 홀로 5판 + 같은 명령 12개를 한꺼번에**

회차 30~34 는 오차가 판마다 **0.008~0.105 로 흔들렸고**, 허용치를 `0.05 → 0.10` 으로
두 번 키웠다. 흔들림의 원인은 부하가 아니라 **재는 구간이 프레임에 한 칸 어긋난 것**이다.

`SceneTree` 를 물려받은 스크립트의 `_process` 는 **노드의 `_process` 보다 먼저** 돈다
(`SceneTree::process` 가 `MainLoop::process` 를 맨 앞에서 부른다). 그래서 프레임 n 에서
게이트가 읽는 `world.now` 에는 **그 프레임의 tick 이 아직 안 들어 있다**:

| | 더한 프레임 | |
|---|---|---|
| 재이는 쪽 (`world.now` 차이) | `delta[k .. E−1]` | k = WARMUP, E = 끝 프레임 |
| 재는 쪽 (회차 30~34) | `delta[k+1 .. E]` | ⇒ 오차 = \|delta[E] − delta[k]\| |
| 재는 쪽 (회차 35) | `delta[k .. E−1]` | ⇒ **오차 = 0** |

**k 가 이 판에서 가장 느린 프레임이라 흔들림이 컸다** — `_find_tree` 가 반지름 40
(≈6561칸)을 훑는 프레임이다. 그래서 오차가 거의 항상 **한 방향**(게임 < 실제)이었다.

| | 오차 | 판정 |
|---|---|---|
| 회차 34 (허용 0.10) · 홀로 3판 | 0.105 · 0.008 · 0.087 | **1/3 이 빨강** — 게임은 멀쩡했다 |
| 회차 35 · 홀로 5판 | 0.000000 × 5 | 5/5 초록 |
| 회차 35 · **12판 동시** | 0.000000 × 12 | **12/12 초록** (구간 0.307~0.380초) |

**허용치를 0.10 → 0.01 로 조였다.** 남는 것이 부동소수 찌꺼기뿐이라 조일 수 있다.
막으려는 고장과의 여유 배수: 안 부른다 **30배** · 델타를 10% 깎는다 **3배**.

#### 회차 35 로 새로 넣은 대조군 — **조인 값만 잡는다**

| 깨뜨린 것 | 오차 | 허용 0.10 (옛) | 허용 0.01 (지금) |
|---|---|---|---|

10% 느린 시계는 **하루를 20분에서 22분으로** 만든다. 게임은 멀쩡히 돌고 나무도 자라므로
REGROW 의 나머지 다섯도 단위 검사 175개도 전부 초록이다 — **오차 하나만** 빨갛다.

것이 아니다. 「진짜 프레임에서도 흐르나」는 위의 첫 줄이 따로 지킨다.

### 칸 색에 안 섞는다 — `CanvasModulate` 한 장이다

밤을 `WorldView.color_at` 에 섞는 쪽이 자연스러워 보이는데, **빛은 매 프레임 변하므로
색 캐시가 통째로 무의미해진다**: 한 화면 2135칸 × 3.32 µs = **7.9 ms** 가 프레임 예산
16667 µs 에서 매 프레임 빠진다 (9절). `CanvasModulate` 는 GPU 의 곱 하나라 공짜다.

**그리고 그 곱은 정확하다** — 재서 확인했다. 같은 화면을 낮과 밤에 굽고
`낮 픽셀 × 하늘빛` 과 맞댄 최대 오차가 **0.90 / 255** 다. 8비트 반올림뿐이라
DRAW 의 기존 허용치 `TOL = 2/255` 를 그대로 쓸 수 있다.

**핫바는 안 어두워진다**: `UI` 가 제 `CanvasLayer` 라 곱이 안 닿는다.
구운 픽셀로 확인 — 핫바 바탕이 **낮 `1c1e26` → 밤 `1c1e26`, 색차 0.0/255** 다.

### **밤빛은 색을 거의 못 돌린다** — 이 회차에서 가장 비싼 발견

`WorldView` 의 부등식(**물은 b > g > r · 땅과 그 위의 것은 b 가 제일 작다**)이
「땅이 물처럼 보이는 일이 없다」를 떠받치고 있다. 하늘빛은 채널마다 **다른 값으로 곱하므로
그 비를 바꾼다** — 파랄수록 땅의 b 가 올라온다.

가장 좁은 자리는 **돌**(`ROCK_COLOR` 0.58 · 0.57 · 0.54)이다. 바닥을 30% 섞고
칸마다 흔드는 ±0.035 까지 얹으면 r 과 b 가 **9% 밖에** 안 벌어져 있다.

| 잰 것 | 밝기 0.290 (회차 31) | 밝기 0.180 (**회차 33**) |
|---|---|---|
| 밤빛의 b/r 문턱 (**넘으면 땅의 부등식이 뒤집힌다**) | **1.0933** (이분법 · 해안 24×24 · 씨앗 20260914) | 같다 — **밝기와 무관하다** |
| 고른 밤빛의 b/r | 1.0714 | **1.0690** |
| 땅의 여유 (`min(r−b, g−b)`) | 낮 0.05470 → 하루 최소 0.01088 | 낮 0.05470 → **하루 최소 0.00698** (위상 0.540) |
| 물의 여유 (`min(b−g, g−r)`) | 낮 0.14168 → 하루 최소 0.04215 | 낮 0.14168 → **하루 최소 0.02615** (위상 0.540) |

**문턱은 안 움직이고 여유만 줄었다.** 부등식을 뒤집는 것은 **b/r 하나**이고 밝기는
양변을 똑같이 곱하기 때문이다 — 그래서 회차 33 은 채널 비를 건드리지 않고 통째로
0.6207 배 했고, 「달빛 아래 바위가 웅덩이가 되나」는 다시 안 재도 됐다.

**둘 다 최소가 위상 0.55 — 해가 막 진 뒤**다. 한밤이 아니다: 여유는 「빛의 밝기」가
아니라 「빛이 얼마나 치우쳤나 × 바닥색이 얼마나 어두운가」가 정하기 때문이다.

`test_day_cycle.gd` 가 **실제 섬의 해안 24×24 칸을 하루 20토막 전부** 곱해 보고 지킨다.
**스폰 둘레로는 못 잰다** — 24×24 가 땅 576 · 물 **0** 이라 물 쪽 판정이 통째로 공허했다
(`measure_window.gd` 가 DRAW 를 해안에 세우는 것과 같은 이유). 해안으로 옮기면
땅 296 · 물 280 이고, **그 수 자체를 검사가 센다**(`MIN_KIND` 40).

### **밤은 얼마나 더 어두워질 수 있나** — 바닥은 8비트가 정한다 (회차 33)

위의 여유는 **float** 다. 화면에 나가는 것은 **8비트로 반올림한 픽셀**이라,
밤빛을 내리면 여유가 같은 비로 줄어서 **float 부등식이 참인 채로 구운 픽셀에서는
r 과 b 가 같은 값**이 되는 자리가 온다 — 「땅이 물처럼 보이지 않는다」가 눈앞에서
무너지는데 `test_inequalities_survive_every_hour` 는 초록이다.

해안 24×24 의 땅 296칸을 한밤에 구워 `round(r×255) − round(b×255)` 의 최소를 잰다:

| 밤의 밝기 | 8비트 r−b 최소 | 순서가 사라진 칸 |
|---|---|---|
| **0.180** (지금) | **1** | 0 |
| 0.144 | 1 | 0 |
| 0.108 | 1 | 0 |
| 0.090 | 1 | 0 |
| 0.072 | **0** | **4** |

**지금은 한 칸 남았다.** 0.18 은 바닥에서 2.5배 위지만 **여유가 1/255 뿐**이라,
다음에 밤을 내리자는 회차는 이 수부터 본다. `test_night_survives_8bit` 이 그 문이다.

**기존 문 넷의 틈이 있었다** — 대조군이 찾았다. 밝기 **0.110** · b/r **1.0893** 이면
밝기 바닥 0.1 초과 · b/r 문턱 1.09 미만 · float 여유 0.00316 으로 양수 · DRAW 의 밤
상한 0.30 미만이라 **넷이 다 초록인데** 구운 픽셀에서 땅 한 칸의 순서가 사라진다.
회차 33 의 8비트 검사는 그 틈을 막으려고 세웠고, 대조군이 그 색을 그대로 쓴다.

### DAY 게이트 (`tools/tests/measure_day.gd`) — **배선**

```
DAY 하루 1200 s · 표본 24개 (50 s 간격) · 여명 96 s
DAY 한 바퀴  제일 밝음 1.000 (위상 0.250) · 제일 어두움 0.180 (위상 0.542) · 낮 12/24 표본
DAY ok (최대 어긋남 0.0000 · 낮 10 분 + 밤 10 분 · 표본 24 + 따라가기 5 프레임)
HEADGATE ok (MOVE 0 · WORLD 0 · COLLIDE 0 · CAMERA 0 · CHOP 0 · REGROW 0 · DAY 0 · 구간 7/7)
```

**최대 어긋남 0.0000** 이다. main.gd 는 `world.tick(delta)` **다음에** 하늘을 칠하므로
게이트가 읽는 `world.now` 가 하늘이 계산된 바로 그 값이다 — 한 프레임 어긋남조차 없다.
허용치 `TOL = 0.01` 은 낮과 밤의 차(0.71)의 1/71 이라, 뒤처짐은 봐주고 배선 구멍은 못 빠진다.

**`Sky` 가 어느 캔버스에 있나를 RID 로 묻는다** — 이름도 부모도 아니다. `CanvasModulate` 는
제가 속한 캔버스를 물들이므로 **곱이 닿는 범위가 곧 규칙**이고, `UI` 안으로 옮기면
월드는 밝은 채 가방만 깜깜해진다 (실측: 핫바 바탕 `1c1e26` → `08090b`, 색차 27.0/255).

**그 하늘을 경로로 찾으면 안 된다** — 대조군이 게이트를 한 번 고치게 했다.
처음에는 `_main.get_node_or_null("Sky")` 로 집었는데, 하늘을 `UI` 로 옮기는 순간
그 경로가 비어서 게이트가 **「하늘이 없다」로 죽고** RID 검사는 한 번도 안 돌았다 —
정작 재려던 「엉뚱한 캔버스에 있는 하늘」을 영영 못 보는 가짜 가지였다.
그래서 **main.gd 가 실제로 물들이는 그 노드**(`main.sky`, 밖에서 보인다)를 집는다.
그래야 노드를 옮기고 배선까지 따라 옮긴 판 — **사람이 실수하는 모양 그대로** — 이
RID 검사에 걸린다.

### DRAW `[밤]` 구간 (`tools/tests/measure_window.gd`) — **픽셀**

```
DRAW [서서]      표본 7750 · 불일치 0 · 최대 색차 0.8/255 · 물 49.6% · 채운 횟수 2
DRAW [걷고 48px] 표본 7750 · 불일치 0 · 최대 색차 0.8/255 · 물 45.2% · 채운 횟수 5
DRAW [밤]        표본 7750 · 불일치 0 · 최대 색차 0.9/255 · 물 45.2% · 채운 횟수 5
DRAW [밤] 하늘빛 2c2e2f (밝기 0.180) · 위상 0.750 · 핫바 낮 1c1e26 → 밤 1c1e26 (색차 0.0/255) · 채운 횟수 5 → 5
```

**「화면이 하루를 안다」는 픽셀로만 증명된다.** 시계를 반 바퀴 돌려 한밤에 세우고
7750 점을 `칸 색 × 하늘빛` 과 맞춘다 — `main.gd` 가 `Sky` 를 안 물들이면 낮 색이
그대로 나와 여기서만 빨개진다. **채운 횟수 5 → 5** 가 「밤은 곱 하나지 칸 색이 아니다」를
지키는 줄이다: 밤을 캐시에 섞었으면 화면은 똑같이 어두워지는데 이 수만 오른다.

### 사람이 밤을 볼 수 있어야 한다 — `NARU_SHOT_NOW`

`shot.sh` 는 **시각을 못 골랐다**. 하루가 20분이라 밤 화면을 보려면 10분을 기다려야 하고
무인 루프에는 아예 길이 없다 — **화면 기능인데 사람이 화면을 못 보는** 자리였다.
`NARU_SHOT_NOW=<게임초>` 로 그 시각에 세우고 굽는다. 시계가 없는 씬에 주면 **에러로
죽는다**: 조용히 한낮을 구우면 사람은 그 그림을 「밤이 이렇구나」로 읽는다.

```
NARU_SHOT_NOW=600 tools/loop/shot.sh /tmp/night.png
SHOT 960x540  색 117개  가장 넓은 한 색 5.4%  600 s (위상 0.750 · 밤 · 밝기 0.000)
```

**회차 33 에서 다시 구웠다** (밤 0.290 → 0.180 · 1920×1080 창 · 논리 960×540):

| 게임 시각 | 위상 | 밝기 | 색 수 (밤 0.290) | 색 수 (**밤 0.180**) | 가장 넓은 한 색 |
|---|---|---|---|---|---|
| 0 s (한낮) | 0.250 | 1.000 | 1000 | **1000** | 1.4% |
| 250 s | 0.459 | 1.000 | 1000 | 1000 | 1.4% |
| 300 s (해 지는 한가운데) | 0.500 | **0.497** | 603 | **511** | 1.7% |
| 400 s | 0.584 | 0.000 | 200 | **117** | 5.4% |
| 600 s (한밤) | 0.750 | 0.000 | 200 | **117** | 5.4% |

**밤은 화면의 색 수를 8.5배 줄인다** (1000 → 117): 0.18 을 곱하면 8비트 계단 256개가
46개로 접힌다. 0.29 일 때는 74개였다 — **어둡게 한 값이 그대로 색 수로 나온다.**
`--max-flat` 은 1.4% → **5.4%** 로 올랐다 (0.29 때는 2.9%). 아직 게이트가 아니라
**적어 두는 값**이지만, 밤에 색이 더 필요해지면(등불 · 이로치) 여기가 먼저 문턱이 된다.
