> **이 파일은 혼자 선다.** 다른 문서를 안 봐도 읽힌다.
>
> **값보다 「조건」이 중요하다.** 아래 값은 전부 어떤 기계 · 어떤 엔진 버전 위에서

## 1. 화면 (2026-09-13 실측 · **타일은 2026-09-14 바퀴 15 에 다시 쟀다**)

**조건: `stretch/mode=viewport` + `scale_mode=integer` + `aspect=keep`, 창 override 1920×1080**

실제로 창을 띄워서 잰 값이다 (`scripts/main.gd` 가 찍는다):

```
VIEWPORT 960 x 540
WINDOW   1920 x 1080
SCALE    2.00 x
```

| 값 | 무엇 | 왜 그 값인가 |
|---|---|---|
| **960 × 540** | 논리 해상도 (= 보이는 월드 범위) | **1080p 정수 2배 · 4K 정수 4배.** 소수 배율은 도트 하나를 화면에서 어떤 건 1px, 어떤 건 2px 로 만들어 걸을 때 얼룩이 흐른다 |
| **1920 × 1080** | 창 크기 | 논리 화면을 정확히 2배로 늘려 붙인다 |
| **2.00 ×** | 실측 배율 | 정수다 |
| **30 × 16.875 칸** | 보이는 타일 수 | 타일 **32px** 기준(48 → 32, 사람). 스타듀 1080p 100% 줌과 같다. `test_visible_tiles` 가 강제한다 — **해상도와 타일 둘 중 아무거나** 바뀌면 빨강 |

**대가**: UI 도 960×540 좌표계에서 만들어야 하고, 폰트가 통째로 2배로 늘어나므로
**비트맵 픽셀 폰트가 필요하다** — 기본 폰트는 늘리면 뭉갠다.

### 실측 게이트 `tools/tests/measure_window.gd` 의 VIEW 절반 (2026-09-14 실측)

> **바퀴 14 에 `measure_view.gd` 와 `measure_draw.gd` 를 한 파일로 합쳤다** — 둘 다
> 창이 필요하고 둘 다 메인 씬을 세운다. 창 여는 횟수가 곧 포커스 도둑질이다 (11절).
> **잰 값은 글자 하나 안 달라졌다** (아래 블록은 합친 뒤 다시 잰 것이다).

위 표는 `test_project_settings.gd` 가 **project.godot 의 글자**를 읽어 강제한다.
글자가 맞아도 실행 중에 카메라 줌이나 창 크기를 만지면 눈에 보이는 칸은 달라진다 —
그래서 **실제 창을 띄워** 다시 잰다 (`check.sh tests` 가 `--headless` 없이 부른다).

```
VIEW 논리 960x540 · 창 1920x1080 · 배율 2.00x · 카메라 1.00x · 타일 32px · 보이는 칸 30.00 x 16.88
VIEW ok (드라이버 macOS · 프레임 5)
```

- 배율은 나눗셈이 아니라 **`root.get_final_transform()`** 에서 잰다.
- 보이는 칸은 **`get_canvas_transform()`** 으로 월드 좌표로 환산해서 잰다 —
  카메라 줌이 곧 시야 이득이라 여기를 막아야 한다 (BACKLOG P1 「줌 없음」).

**대조군 2종** (`redteam.sh` 에 박아 뒀다):

| 일부러 깨뜨린 것 | 단위 검사 | 화면 실측 |
|---|---|---|
| 카메라 `zoom` 을 (2,2) 로 | (2026-09-13: `18 passed`) | **잰 값 보이는 칸 15.00 x 8.44** ✅ (타일 48 일 때는 10.00 x 5.62) |
| 실행 중 `window_set_size(1600, 900)` | `18 passed, 0 failed` | **잰 값 창 1600x900 · 배율 1.00x** ✅ |

두 번째가 정수 배율의 성질을 그대로 보여준다: 1600/960 = 1.66 이 아니라 **1** 로 떨어진다.

**첫 줄은 바퀴 8 에서 겨눌 곳이 바뀌었다.** 그때는 `main.tscn` 에 카메라를 하나 덧붙였는데,
진짜 카메라가 생긴 뒤로는 **먼저 트리에 들어온 플레이어의 카메라가 화면을 잡는다(선착순)** —
덧붙인 카메라는 아무 일도 안 한다. **가짜 대조군이 될 뻔한 자리다.** 지금은 `player.tscn` 의
그 카메라의 줌을 직접 건다. 대신 단위 검사(`test_camera_zoom_is_one`)도 같이 잡으므로,
「단위는 초록인데 실측만 잡는」 쪽은 8절의 **실행 중 줌**이 맡는다.

## 2. 격리 — **macOS 는 XDG 를 무시한다** (2026-09-13 실측)

**이걸 안 재고 넘어갈 뻔했다.** `XDG_DATA_HOME` 등을 설정해두고 「격리했다」고 믿는 것이
정확히 가짜 게이트다.

| 방법 | `user://` 가 실제로 간 곳 | 홈의 Godot 디렉터리 |
|---|---|---|
| `XDG_*` 만 설정 | `~/Library/Application Support/Godot/app_userdata/Naru` | **mtime 이 실행 시각으로 갱신됨** ❌ |
| **`HOME` 을 돌린다** | `.godot-home/Library/Application Support/Godot/app_userdata/Naru` | **mtime 안 바뀜** ✅ |

- 그래서 `tools/loop/godot.sh` 는 **`HOME` 자체를 프로젝트 안으로 돌린다.**
  `XDG_*` 도 같이 두는 것은 리눅스에서 도는 경우를 위해서다.
- **격리는 설정이 아니라 「입구」로 지켜진다.** `test_isolation.gd` 가
  `OS.get_user_data_dir()` 이 프로젝트 안인지 재므로, **`godot.sh` 를 우회한 실행은
  그 자리에서 빨개진다.** 실측:

  ```
  FAIL test_isolation.gd :: test_user_data_is_project_local
       — 잰 값: /Users/tuna/Library/Application Support/Godot/app_userdata/Naru
  ```

## 3b. 화면 캡처 (2026-09-13 실측)

**`screencapture` 는 못 쓴다** — macOS 화면 기록 권한에 막힌다
(`could not create image from display`). 무인 루프가 권한 대화상자를 넘길 방법이 없다.

**Godot 자신의 프레임버퍼를 읽는다** (`tools/qa/shot.gd`). 권한이 필요 없고,
화면에 보이는 것이 아니라 **게임이 그린 것**을 읽으므로 다른 창이 겹쳐도 상관없다.

| 방식 | 결과 |
|---|---|
| `--headless` + 뷰포트 텍스처 | **안 된다** — 렌더러가 더미라 텍스처가 빈다 (출력 없음) |
| **창을 띄우고 뷰포트 텍스처** | **된다** — `SHOT 960x540 색 3개 가장 넓은 한 색 50.0%` |

- 그래서 `tools/loop/shot.sh` 는 `--headless` 를 **쓰지 않는다.** 창이 잠깐 떴다 사라진다.
- **「저장됨」은 증거가 아니다** — 크기 · 색 수 · 가장 넓은 한 색의 비율을 같이 찍는다.
  `--max-flat <퍼센트>` 로 「거의 단색인 화면」을 빨갛게 만들 수 있다.
- 대조군: 상한 40% → 빈 씬(50%)이 잡힘 / 없는 씬 → `SHOT ERROR` / 헤드리스 → 출력 없음.

### 섬 모양은 운이 아니라 **부등식**이다

| 보장 | 왜 참인가 |
|---|---|
| 테두리는 **항상 물** | 감쇠 `FALLOFF_GAIN 1.25` > 잡음 최대 `1.0` → 높이 ≤ -0.25 < 해수면 0.30 |
| 한가운데는 **항상 땅** | 잡음 바닥 `NOISE_FLOOR 0.35` > 해수면 `SEA_LEVEL 0.30`, 중심 감쇠 ≈ 0 |

씨앗을 몇 개 뽑아 봐서 「되더라」가 아니라 상수끼리의 부등식이다.
**상수를 만지면 이 두 줄부터 다시 계산해야 한다** — 검사(`test_border_is_always_water`,
`test_spawn_is_always_land`)가 여러 씨앗으로 지키지만, 검사는 표본이고 위 두 줄은 증명이다.

## 7. 충돌 (2026-09-14 실측 · **바퀴 15 에 타일 32 로 다시 쟀다**)

**조건: `scripts/world_collide.gd` · Godot 4.7.2 · macOS M5 Pro · 헤드리스 ·
물리 60 Hz · 씨앗 20260914 · 메인 씬을 통째로 띄워 잼**

| 값 | 무엇 |
|---|---|
| **14.0 px** | 몸 반폭(`HALF`). 몸 28×28 이 32 타일 안에서 **양옆 2px 씩 남는다**. **숫자가 아니라 식이다**: `PlayerMotion.TILE * 0.5 - 2.0` — 박아 두면 타일이 작아질 때 안 따라와 1칸 통로에 낀다 |
| **0.01 px** | 벽에 붙일 때 남기는 틈(`EPS`). 0 이면 붙은 칸이 겹친 칸으로 읽혀 다음 프레임이 흔들린다 |
| **169.71 px/s** | 해안을 탈 때의 세로 속력 = 240 / √2. **벽에 붙어도 안 줄인다** |
| **3.345 µs** | 「이 칸이 막나」 한 번 (10만 회 334.5 ms · 막힘 67.7%). 한 틱에 네 번쯤 묻는다 |

**몸이 타일보다 좁아야 하는 이유**: `HALF` 가 타일 반(16)과 같으면 폭 1칸(32px) 통로에서
부동소수 한 톨에 걸려 낀다. `14 < 16` 은 검사(`test_body_is_narrower_than_a_tile`)가 지킨다.

**그리는 네모는 이보다 넓다** — 몸통 48×48 은 타일 1.5칸이고 충돌 상자는 28×28 이다.
벽에 붙으면 네모가 막힌 칸에 **10px 걸쳐 보인다.** 관례(코어 키퍼)는 몸통 1칸 폭 ·
상자는 발밑 반 칸이라 **그림이 정해질 때 같이 정할 값**이다 (BACKLOG P2).

### 미끄러짐은 **축을 따로 푸는 것**에서 나온다

x 를 풀고 y 를 푼다 — 막힌 축만 죽고 나머지는 그대로 간다.
「벽에 닿았으니 통째로 정지」가 아니고, 남은 몫을 다시 정규화하지도 않는다.
**물리 엔진을 안 쓴다**: 65536칸에 정적 몸을 세울 수 없고, 창 주변만 세우면 결과가
「지금 무엇이 세워져 있나」에 달린다. 격자에 대고 풀면 **같은 입력이 언제나 같은 자리**다
(GDD D-1 서버 재현성 · C-4 원정 보고 검증).

### 실측 게이트 `tools/tests/measure_collide.gd` (2026-09-14 실측)

## 9. 그리기 (2026-09-14 실측 · **바퀴 15 에 타일 32 로 다시 쟀다**)

**조건: 씨앗 20260914 · 창 1920×1080 · 논리 960×540 · 줌 1 · 60Hz · gl_compatibility**

임시 격자를 걷어냈다. 화면에 있는 것은 **진짜 월드**다 — 파랗게 보이는 칸이 곧
`WorldCollide` 가 막는 칸이다.

| 값 | 무엇 |
|---|---|
| **558 칸** | 한 화면에 걸리는 칸 수 (31 × 18). 어긋난 화면의 **최대**다 (48px 이던 때 273) |
| **527 칸** | 실측 게이트가 해안에서 실제로 그린 칸 수 (31 × 17) |
| **31 × 17 칸** | 칸 경계에 딱 맞춘 화면. 960/32 = 30 은 떨어지고 540/32 = 16.875 는 안 떨어진다 |
| **65536 칸** | 월드 전체. **117배다**(48px 이던 때 240배) — 통째로 그려도 사람 눈에는 똑같이 보인다 |
| **6.71 µs** | 한 칸의 색을 구하는 비용 (잡음을 두 번 돈다: `tile_at` + `height_at`). **타일 크기와 무관하다** |
| **3.74 ms** | 558칸 한 판 = **60Hz 한 프레임 예산 16.67 ms 의 22.5%**. 타일이 반으로 작아져 **두 배 비싸졌다** |

### 색이 곧 지형이다 — 덧칠이 아니다

물이냐 땅이냐는 **`WorldGen.tile_at` 이 정한다.** `WorldView` 가 `h > SEA_LEVEL` 을
다시 쓰지 않는 이유가 이것이다 — 두 벌을 두면 언젠가 한쪽만 고쳐져 **보이는 땅에
못 서는 날**이 온다. 그 안에서의 명암만 높이로 섞는다.

**흔들기는 세 채널에 같은 양을 더한다**(`TINT` ±0.035 = 8비트로 ±9). 그래서
**물은 언제나 b > g > r · 땅은 언제나 g > r > b** 이고, 이 부등식을 `test_world_view.gd`
가 7396칸으로 잰다. 곱하거나 채널마다 다르게 흔들면 **물처럼 보이는 땅**이 생긴다.

`DEEP_AT = -0.25` 는 고른 값이 아니라 **계산된 값**이다: 월드 밖은 감쇠가 1.25 로
포화하므로 높이가 `0.35 + 0.65 - 1.25 = -0.25` 를 넘을 수 없다 → **월드 밖은 자동으로
정확히 `DEEP`** 이고 분기가 필요 없다 (6절의 「섬 모양은 부등식이 보장한다」와 같은 수법).

### 화면이 단색이면 안 된다 — 칸마다 흔드는 진짜 이유

| | 칸 | 색 수 | 가장 넓은 한 색 |
|---|---|---|---|
| 임시 격자 (바퀴 8) | — | 3개 | **50.0%** |
| 진짜 월드 · 타일 48 (바퀴 9) | 273 | **217개** | **1.3%** |
| 진짜 월드 · 타일 32 (바퀴 15) | 558 | **349개** | **1.3%** |

**검사의 문턱도 같이 올렸다**: 색 수 100개 → **200개**. 273칸에 100개는 37% 였는데
칸만 558 로 늘리고 문턱을 두면 게이트가 **반으로 헐거워진다** (`test_a_screenful_is_not_flat`).

흔들기가 없으면 스폰 주변은 전부 풀밭이라 한 화면이 거의 단색이 되고,
`shot.sh --max-flat` 이 **아무것도 안 잡는 공허한 상한**이 된다.
32px 격자가 눈에 남는 것은 덤이 아니라 필요다 — 240 px/s 가 7.5칸/초로 보이는지
**사람이 걸어서** 확인하는 유일한 방법이다.

### 색 캐시 — 프레임마다 다시 계산하지 않는다

3.74 ms 는 나무도 몹도 UI 도 없는 지금의 22% 다. 그래서 **칸이 아니라 보이는 범위가
바뀔 때만** 다시 채운다(`main.gd` 의 `_cache` / `_cache_range`).
**96 px(3칸) 걷는 동안 5번** 찼다 — 240 px/s 면 한 축당 초당 7.5번이라 평균 8배 싸다.
타일이 작아지면서 **한 판도 두 배 비싸지고 다시 채우는 빈도도 1.5배가 됐다.**

**대가는 상해도 눈에 안 보이는 것이다** — 캐시가 안 버려지면 화면이 월드에서 미끄러진다.
아래 대조군 ④ 가 **최대 색차 86.0/255** 로 잡는다.

### 실측 게이트 `tools/tests/measure_window.gd` 의 DRAW 절반 (2026-09-14 실측)

> **바퀴 14 에 VIEW 와 한 파일로 합쳤다** (1절·11절). VIEW 를 **먼저** 잰다 —
> DRAW 가 플레이어를 해안으로 순간이동시키므로 순서가 뒤집히면 VIEW 는 「처음 뜬
> 창」이 아니라 「걷다 만 화면」을 재게 된다. **아래 잰 값은 합친 뒤 다시 잰 것이고

## 10. 방향 게이트 — 합성 입력 (2026-09-14 실측)

**조건: 씨앗 20260914 · 논리 960×540 · 줌 1 · 60Hz · Godot 4.7 · macOS**

9절 끝의 흔들림을 고쳤다. `measure_facing.gd` 는 이제 **진짜 커서를 안 뺏는다** —
메인 씬을 제 `SubViewport` 에 세우고 합성 `InputEventMouseMotion` 을 밀어 넣는다.

### 왜 루트 뷰포트로는 안 되나

**루트 뷰포트의 `get_mouse_position()` 은 매번 OS 커서를 되묻는다.** 그래서
`warp_mouse` 로 옮겨 놔도 사람이(또는 다른 프로세스가) 커서를 건드리면 그 값이 이긴다.
**SubViewport 는 밀어 넣은 이벤트만 본다:**

| | 이벤트를 (700,111) 로 밀어 넣은 뒤 | `warp_mouse(5,5)` 한 뒤 |
|---|---|---|
| `SubViewport.get_mouse_position()` | (700, 111) | **(700, 111) — 안 움직인다** |
| `root.get_mouse_position()` | (-104, 225) | (2, 2) |

헤드리스에서도 같다 (SubViewport 쪽은 두 번 다 (700,111)).

### 대조군 — 커서를 흔들면서 돌렸다

두 번째 Godot 을 띄워 매 프레임 `warp_mouse` 로 커서를 휘젓는 **방해 프로세스**를
만들어, 옛 게이트와 새 게이트에 같은 방해를 걸었다. 이걸로 **네 바퀴짜리 흔들림이
처음으로 재현됐다** — 전에는 사람이 마우스를 만질 때만 우연히 나타났다.

| 게이트 | 방해 | 결과 |
|---|---|---|
| 옛 (진짜 커서) | 있음 | **FAIL 13개 · 7구간 전부** · 커서 각 `-155.5°`·`-137.3°`·`-158.2°` (기대 0°·90°·180°) |
| 새 (합성 입력) | 있음 · 헤드리스 | **7구간 전부 ok** · 커서 각 `0.0°`·`90.0°`·`180.0°`·`-90.0°`·`46.0°`·`60.0°` — **오차 0** |
| 새 (합성 입력) | 있음 · 창 띄움 · 15회 | **15/15 초록** |

### 숨어 있던 두 번째 버그 — 유휴 프레임 ≠ 물리 틱

방해를 걸고 재다가 **마우스와 무관한** 실패를 찾았다. 마우스를 안 건드리고
**부하만** 준 12회 중 1회, 첫 구간이 `커서 0.0°`(겨눔은 정확)인데
`방향 (-1,0)`(기대 (1,0))으로 빨갰다.

**원인**: `facing` 은 `_physics_process` 가 정하는데 게이트는 **유휴 프레임**을 셌다.
부하가 걸리면 유휴 4프레임이 물리 한 틱도 못 품는다 — 겨눔은 맞고 방향만 한 틱
뒤처진다. **하필 첫 구간인 이유**: 밀어 넣기 전 SubViewport 의 커서 기본값이 (0,0) 이라
플레이어(화면 한가운데) 기준 **−151°** 다. 플레이어가 먼저 `LEFT` 를 잡아 두고 있다.

**고친 것**: `Engine.get_physics_frames()` 로 **물리 틱을 센다** (`SETTLE_TICKS = 2`).

| 언제 | 부하만 · 창 띄움 | 마우스 방해 · 창 띄움 |
|---|---|---|
| 유휴 프레임을 셀 때 | **12회 중 1회 빨강** | 8회 중 1회 빨강 |
| 물리 틱을 셀 때 | **15회 중 0회** | **15회 중 0회** |

### 구멍은 그대로 막혀 있나 — FACE 대조군 4종

SubViewport 로 옮기면서 **덮던 것을 잃지 않았는지** 물었다. 넷 다 잡는다:

| 대조군 | 잰 값 |
|---|---|
| ① 노드가 커서를 안 읽는다 (`aim_at(...)` → `pass`) | **FAIL 4개** |
| ② 히스테리시스를 건너뛴다 (`resolve` → `nearest`) | **FAIL 1개** (46° 구간) |
| ③ 방향은 맞는데 코가 안 돈다 (`_place_nose()` 제거) | **FAIL 4개** |
| ④ **캔버스 변환을 빼먹는다** (`get_global_mouse_position` → `get_viewport().get_mouse_position`) | **FAIL 6개** |

④ 는 **바퀴 11 에 새로 넣었다.** SubViewport 로 옮겼으니 「카메라의 캔버스 변환을

## 11. 포커스 — **막을 수 없다. 되돌려 줄 뿐이다** (2026-09-14 · 바퀴 13 실측)

### 막으려고 한 6가지 — **전부 뺏겼다**

| 시도 | 창·배율·프레임버퍼 | 포커스 |

  못 될 뿐 **앱은 그대로 앞으로 온다.** 게다가 켜두면 **사람이 직접 띄운 창에서 WASD 가

### 그래서 되돌려 준다 — `NARU_FOCUS_RESTORE=1`

`godot.sh` 가 띄우기 직전의 맨 앞 앱(`lsappinfo` 의 번들 경로)을 기억했다가, 끝났을 때
맨 앞이 그 앱이 아니면 `open` 으로 다시 앞으로 보낸다. **창을 띄우는 두 곳에만 건다** —
`check.sh` 의 VIEW · DRAW 와 `shot.sh`. 사람이 직접 띄운 창에는 안 건다(보는 동안 딴 앱으로
옮겼을 수 있다).

| 조건 | 시작 앞 | 끝 앞 | 되돌아옴 |
|---|---|---|---|
| 되돌리기 **끔** · VIEW | `Finder` | `SystemUIServer` | **NO** |
| 되돌리기 **켬** · VIEW × 3회 | `Finder` | `Finder` | **yes · 3/3** |

`check.sh tests` 한 판: **표본 110 · 뺏김 14 · 시작 앞 = 끝 앞 (`Finder`)**.
계약 한 판(창 3번 — VIEW · DRAW · `shot.sh`): **표본 183 · 뺏김 13 · 시작 앞 = 끝 앞**.
**뺏기는 것은 그대로다** — 창 두 번이 도는 ~1.8초 동안 타이핑은 여전히 Godot 으로 간다.
없어진 것은 **「끝나고도 안 돌아온다」** 쪽이다. 전에는 매번 사람이 손으로 클릭해야 했다.

**남은 길은 「막기」가 아니라 「횟수 줄이기」다** — VIEW 와 DRAW 는 둘 다 창이 필요하고
둘 다 메인 씬을 세운다. 한 프로세스로 합치면 한 판에 창이 **2번 → 1번**이 된다 (BACKLOG).

### 그래서 합쳤다 — `measure_window.gd` (2026-09-14 · 바퀴 14 실측)

`measure_view.gd` + `measure_draw.gd` → **`tools/tests/measure_window.gd` 한 프로세스.**
`check.sh tests` 가 창을 여는 곳은 이제 **하나뿐**이고, 계약 한 판은 **3번 → 2번**이다
(남은 하나는 기준 6 의 `shot.sh`).

| 무엇 | 합치기 전 (바퀴 13) | 합친 뒤 (바퀴 14) |
|---|---|---|
| `check.sh tests` 한 판 | 표본 110 · **뺏김 14** | 표본 102 · **뺏김 9** |
| 계약 한 판 | 표본 183 · **뺏김 13** | 표본 166 · **뺏김 12** |
| 창 여는 횟수 (`tests` / 계약) | 2 / 3 | **1 / 2** |
| 게이트 자체 | VIEW 0.58s + DRAW 1.25s = **1.83s** | **1.29s** (창 한 번) |
| 계약 한 판 | 21.86s (바퀴 13) | **20.28s** |

`redteam.sh` 한 판(계약 31회): 창 **93번 → 62번** · **`REDTEAM 31 잡음, 0 놓침` · 7분 41초**
(바퀴 10 은 30개 · **10분 03초** · 1 놓침 — 놓친 것은 사람 마우스에 흔들린 `FACE` 였다).

둘 다 시작 앞 = 끝 앞 (`iTerm2`). **뺏김이 0 이 되지는 않는다** — 창이 한 번이라도
뜨면 뺏긴다. 줄어든 것은 **뺏기는 횟수와 그 총 시간**이다.

**합치면 새로 생기는 구멍이 하나 있다 — 반쪽만 돌고 죽는 것.** 따로 돌 때는 프로세스가
죽으면 그 게이트가 통째로 침묵했는데, 합친 뒤에는 **VIEW 는 찍고 DRAW 중간에 죽는** 일이
생긴다. 그래서 게이트가 끝에 `WINGATE ok (VIEW 0 · DRAW 0 · 창 한 번)` 을 찍고
`check.sh` 가 **그 줄까지 셋을 다 본다.** 대조군(창 게이트를 1초에 끊었다):
`^VIEW ` 와 `^DRAW \[` 는 **둘 다 맞는데** `WINGATE` 만 없어서 `WINGATE FAIL 게이트가
끝까지 못 갔다` 로 잡혔다 — 그 줄이 없었으면 **잘린 판이 초록으로 보였다.**

이름이 `WINDOW` 가 아니라 `WINGATE` 인 이유: `main.gd` 가 시작할 때 `WINDOW   1920 x 1080`
을 찍는다. `^WINDOW ` 로 grep 하면 **게이트가 한 줄도 안 찍어도 그 배너가 걸린다.**
